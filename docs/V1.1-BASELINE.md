# SENTINEL Enterprise V1.1 protected baseline

V1.1 extends the existing .NET 10 WPF Windows desktop. It does not replace the desktop stack, rewrite the security engines, or introduce a server/database dependency. The historical `v1.0.0` release and its published binary assets remain unchanged. V1.1 uses a separate `v1.1.0` tag and distribution names.

## Architecture and compatibility boundaries

| Layer | Existing responsibility | V1.1 preservation requirement |
| --- | --- | --- |
| `Sentinel.Core` | Evidence/asset/identity models, offline Northstar lab, risk, defensive paths, root-cause remediation, compliance, local analyst | Existing evidence-derived algorithms, IDs, confidence semantics and synthetic provenance remain authoritative. |
| `Sentinel.Infrastructure` | SQLite repository, application coordinator, report exports, protected connector secrets | Existing persistence, atomic mutations, reporting, authorization boundaries and DPAPI behavior are preserved. |
| `Sentinel.Engines` | Explicitly scoped network, local endpoint, web and DNS/email posture collectors; authorized evidence import | No exploitation or autonomous collection is introduced by the redesign. Unavailable measurements continue to be unknown. |
| `Sentinel.Service` | Least-privilege maintenance, health heartbeat, owned-directory retention/audit | Desktop reads health evidence; the service does not autonomously scan networks. |
| `Sentinel.Desktop` | WPF shell, real route controls, analyst/graph/report/assessment workflows | V1.1 changes presentation and desktop interaction around the existing coordinator, not the truth source. |
| `Sentinel.Cli` | Offline and authorized assessment/testing commands | Existing CLI remains available for automated and operational checks. |
| Installer/release | Self-contained win-x64 WPF/service payload, NSIS installer, immutable release assets and checksum round trip | Preserve absolute helper resolution, dependency preflight, Windows install/service/upgrade/uninstall gates and fail-closed publishing. |

Standalone operator evidence remains in `%LOCALAPPDATA%\Sentinel\sentinel.db`. The service uses protected `%PROGRAMDATA%\Sentinel\ServiceState` and `ServiceLogs` directories. SQLite schema version 2 stores current Demo and Live snapshots separately, immutable snapshot history, settings, audit entries and graph projections. Migration from schema 1 backfills the graph; a newer schema fails with a readable compatibility error. A UI upgrade must not erase or recreate this database.

## Working flows to preserve

1. **First launch and workspaces.** The desktop initializes SQLite and reads settings. A clean profile offers Demo Organization and Live Environment. Reopening restores the last environment. The Demo lab uses actual storage and analytics and makes no network requests. Live starts with no assessed evidence: an inventory alone cannot imply a perfect score.
2. **Offline Northstar organization.** The existing deterministic fixture contains 250 endpoints, 12 servers, network appliances, cloud resources, web properties, identities, certificates, findings, historical scenarios and defensive paths. Synthetic addresses use `.example.invalid`; all observations retain synthetic provenance. The UI renders this real evidence instead of hand-entered demonstration metrics.
3. **Authorized assessment.** The operator selects an available collector and explicitly confirms an exact, fresh scope and authorizing identity. Hosts, URLs, ports, concurrency and timeouts are bounded. Demo cannot invoke live collection. Authorization and scope are audited before collection.
4. **Safe cancellation and failures.** The coordinator serializes workspace mutations, collects into a candidate copy and commits only completed results. Cancellation/collector failure records a run state and correlation ID while preserving prior evidence. Interrupted running assessments are recovered as failed when reopening. The UI keeps progress/cancel/close behavior and readable failures with technical log details.
5. **Asset inventory and business context.** Search/type filtering and row selection expose the stored asset and observations. Owner/criticality edits require a reason, create history/audit evidence and recalculate contextual risk. Operator retirement does not remove unresolved exposure or vulnerability evidence.
6. **Findings and dispositions.** Search, severity/state filters and selection link to affected assets, CVE metadata, evidence, controls, remediation and verification. Fixed/accepted-risk/false-positive decisions are persisted and audited. Risk acceptance needs a future review date; expired acceptance remains relevant. UI workflow labels must not manufacture a verified fix.
7. **Evidence and defensive paths.** Graph nodes/edges retain real IDs, relationships, provenance/confidence and finding references. Paths are evidence-supported explanations and never executed. Breakpoints explain defensive actions and verification. Empty path/graph states cannot imply a completed assessment.
8. **Contextual risk/remediation/compliance.** Existing risk combines severity, confidence, exploitability metadata, exposure, business criticality, privilege/reach, defensive paths and compensating controls. Category scores require coverage. Remediation groups root causes and reports modeled reductions as estimates, dependent on verification. NIST CSF 2.0/CIS mappings are evidence mappings, not certification claims.
9. **Monitoring/incidents.** Scan/history/score events display timestamps, source and evidence. A case is created from existing finding IDs, then updates owner/status/notes with audit/history. A case alone does not establish a confirmed breach.
10. **Reports.** Seven report kinds export through the same reporting engine to JSON, CSV, HTML and PDF. Export uses a cloned snapshot and records an audit event. Existing escaping, CSV formula protection, PDF structure, cancellation and invalid-destination protections remain in force.
11. **Offline analyst and integrations.** Evidence-grounded analyst answers preserve confidence and distinguish inference, with record IDs that support navigation. External AI is optional and must not invent citations. Connector availability remains honest: authorized export import is supported; an unimplemented direct API connection must not appear connected.
12. **Settings and local privacy.** Dark/Light/System theme and retention settings persist. Retention trims historical records while keeping current unresolved evidence. Connector secrets use current-user Windows DPAPI and are excluded from reports. Normal operation needs no Visual Studio or source tree.
13. **Windows packaging/upgrade.** Setup bundles runtime/native SQLite/desktop/service, invokes explicit native Windows PowerShell helpers with known module paths, preflights dependencies, installs the service as LocalService and produces shortcuts/uninstaller. Same-version and V1.0-to-V1.1 upgrade must preserve evidence/settings. Uninstall removes app/service and retains operator evidence/audit as documented.

## Baseline validation and evidence

Before UI edits, a fresh full Release solution build with warnings treated as errors, product tests and engine tests passed in [Windows baseline run 37614951188](https://github.com/ever2vip/SENTINEL/actions/runs/37614951188). The gate recorded **zero compilation warnings/errors, 92 product checks passed, zero failures, 1 machine-dependent Windows local-posture skip, and 17 engine checks passed with zero failures**. Redesign edits began only after that completed gate. Execution evidence is recorded by the workflow; source review is not a passed runtime check. The historical V1.0 published workflow also passed 10 Windows install/service/launch/upgrade/uninstall checks. Linux had 93 product checks passed because endpoint availability follows the host platform.

Run after redesign:

```powershell
dotnet build Sentinel.sln -c Release --warnaserror
dotnet run --project tests/Sentinel.Tests/Sentinel.Tests.csproj -c Release
dotnet run --project tests/Sentinel.EngineTests/Sentinel.EngineTests.csproj -c Release
./scripts/verify-desktop.ps1 -DesktopDirectory '<installed path>\Desktop' -EvidenceDirectory artifacts/desktop-verification
```

The new WPF harness loads the actual specified installed Desktop assembly, creates an isolated operator profile and exercises real first-launch/Demo/navigation/control workflows on an STA dispatcher. It exports PNGs, viewport/control diagnostics and machine-readable results. The rendering matrix is 20 routes × Dark/Light × 1366×768, 1920×1080, 2560×1440 × 100/125/150% **effective** sizing. Effective scaling uses logical DIP viewport sizes and renders at the corresponding pixel density; it is explicitly labeled simulated display scaling. Native machine/window DPI is recorded separately. This does not claim to have changed Windows display settings or tested physical monitors.

Automated rendered snapshots and layout diagnostics complement actual PNG inspection. They do not by themselves prove every hover/focus state, physical display configuration, external connector or OS combination. Any skipped or unavailable check must remain visible in verification results. Packaging/publication is gated on tests, real installed-assembly desktop acceptance, service/upgrade/uninstall and release download checksum verification.
